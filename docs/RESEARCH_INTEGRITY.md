# Research integrity policy

AlignmentDelta is intended to support auditable academic research. The following rules apply to future scientific code and outputs:

1. Never fabricate measurements.
2. Never fabricate model outputs.
3. Never invent benchmark results.
4. No result row may exist unless its evaluation actually ran.
5. Failed runs remain auditable and may not be silently discarded.
6. Synthetic/mock data is allowed only in tests and must never enter scientific result directories.
7. Record the exact source model identifier for every scientific run.
8. Record immutable model revision/commit hashes whenever obtainable.
9. Record tokenizer revision.
10. Record the chat template.
11. Record the system prompt.
12. Record decoding parameters.
13. Record random seeds.
14. Record quantization configuration.
15. Record software and environment metadata.
16. Record benchmark name and benchmark version/revision.
17. Record transformation implementation and transformation parameters.
18. Distinguish exploratory/pilot runs from confirmatory experiments.
19. Do not change evaluation criteria after inspecting results without documenting the change.
20. Do not remove negative or null findings because they weaken a hypothesis.

Generated research artifacts must be traceable to:

- the Git commit;
- the experiment configuration;
- the model revision;
- the environment manifest.

`artifacts/` is for diagnostics and reproducibility outputs. `results/` is reserved for actual scientific result files generated by completed, documented executions. No scientific results are created by Step 1.0, Step 1.1, or Step 1.2.

## Run-contract extensions

- Every scientific observation belongs to exactly one concrete run.
- Every run references exactly one experiment condition and source Git commit.
- A dirty tree must be recorded and should normally be prohibited for confirmatory runs.
- Failed runs cannot be converted into successful runs under the same run ID; reruns receive new IDs.
- Invalidated runs remain preserved with a reason and analysis-exclusion decision.
- Pilot and confirmatory runs remain distinguishable.
- Condition IDs hash scientific configuration only, never hardware-only properties.
- Validation and dry-run commands cannot generate scientific outputs.
- Paper results must be traceable to original run metadata.


- Record the Torch/CUDA environment for every run; driver-reported CUDA and `torch.version.cuda` are distinct fields.
- Quantized and non-quantized executions cannot be pooled without explicit protocol justification.
- Record precision mode, resolved device type, and GPU model.
- Pilot and confirmatory experiments may use different hardware, but hardware differences remain auditable.
- Infrastructure diagnostics are not scientific observations.
- Cloud runtime resets or failures must not generate completed experiment records.
- Never silently fall back from GPU to CPU or from one precision mode to another; record the resolved condition explicitly.
